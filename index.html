Practical Aspects of Neural Networks

A working method for the moment every practitioner meets: the model trains, the numbers come out, and they aren't good enough. This is the systematic path from symptom to fix — diagnosis, tuning, verification, measurement, and judgment — built around one real customer-segmentation model, end to end.

Framing

What do you do when your model does not work?

Training a neural network takes a few lines of code. Knowing what to change when it does not work is the skill that separates a beginner from someone who can be trusted with a production model.

This is a systematic way to answer that question, and it is the spine of everything that follows:

Diagnose

  • Match the symptom to the knob before touching anything

Tune

  • Adjust the settings that matter most, in the right order

Verify

  • Confirm backpropagation itself is computing correctly

Measure

  • Choose a metric that tells the truth about performance

Judge

  • Compare against human-level performance, not a vacuum

Extend

  • Handle inputs that carry more than one label at once

Working example

The business case

A bank wants to categorize its customers so it can advertise a credit card product to the right people. As the data scientist, the task is to classify customers into one of four segments based on their spending, family size, age, and marital status — a 4-class classification problem that will carry every idea in this post.

The data

After loading the raw customer records, two columns are dropped immediately: a row ID, which carries no information about the customer, and an anonymized category with no clear business meaning. In a real project a column like that would only be dropped after an experiment showed it didn't help — not because it can't be explained.

Why fit the scaler only on training data?

The standard scaler learns its mean and standard deviation from whatever it is fitted on. Fit it on validation or test data too, and information the model is supposed to never see leaks into training — scores look better than they really are. This is data leakage, a classic reason a model that looked great in the notebook fails in production.

Class index, not one-hot

PyTorch's cross-entropy loss takes the class index as the target and raw logits (not probabilities) from the last layer — it applies softmax internally. Adding a softmax layer before it applies softmax twice: the code still runs without error, but the model learns more slowly and the loss values become misleading. It's one of the most common PyTorch bugs, and a favorite interview question.

Working example

The baseline model

Before trying anything clever, every project needs a baseline: a simple model whose numbers every later change gets compared against. Without one, nobody can say whether a change actually helped.

A 6-layer baseline — ReLU between every linear layer, raw logits out

21 input features → 64 → 32 → 16 → 8 → 4 class logits. Weights use Glorot (Xavier) initialization; optimizer is Adam with cross-entropy loss.

View the model definition 
def create_baseline(in_features, n_classes=4):
    model = nn.Sequential(
        nn.Linear(in_features, 64), nn.ReLU(),
        nn.Linear(64, 32), nn.ReLU(),
        nn.Linear(32, 16), nn.ReLU(),
        nn.Linear(16, 8), nn.ReLU(),
        nn.Linear(8, n_classes),   # raw logits — no softmax here
    )
    for layer in model:
        if isinstance(layer, nn.Linear):
            nn.init.xavier_uniform_(layer.weight)
            nn.init.zeros_(layer.bias)
    return model

The training loop follows the same four steps in every PyTorch project: clear old gradients, run the forward pass and compute the loss, run backpropagation, update the weights. Accuracy alone can hide poor performance on individual classes, so precision, recall and F1 are tracked too, averaged across the four classes.

After 10 epochs, both training and validation loss are still high and still falling, and precision and recall are far from where they should be — the model hasn't finished learning. Roughly half of the customers are classified correctly. That's the number everything else in this post improves on.

Core idea

Orthogonalization: one knob, one problem

There's a long list of things that could help a weak baseline: more epochs, a deeper network, regularization, a different optimizer, more data. Tried at random, that list burns months without ever confirming what actually helped.

Think of a DJ mixer. One knob controls pitch, one controls amplitude, one adds bass. If the DJ wants more bass, there is exactly one knob to turn. If one knob changed pitch, amplitude, and bass together, nobody could control the sound. Every idea for improving a model is a knob — the skill is knowing which knob fixes which symptom, and turning only one at a time. Change three things in one run and the metric moves, and nobody can say which change caused it.

Click a symptom to see the knobs that actually target it:

Diagnosis: underfitting (high bias)

The model hasn't learned the training data well

  • A bigger network — more layers or more neurons
  • A different optimizer, preferably Adam
  • Training for more epochs

Diagnosis: overfitting (high variance)

The model memorizes training examples instead of generalizing

  • Regularization — L2, dropout, batch normalization
  • A simpler network
  • More training data, ideally diverse samples (new cities, age groups — not more of what's already seen)

Diagnosis: validation set too small or unrepresentative

Rare, but a real failure mode

  • A bigger, more representative validation set
  • The model (or its hyperparameters) likely overfit the validation set itself — not the loss function, which would show the same problem on validation too

Why not just collect more data?

It looks like the safest answer, but it shouldn't be the first move: some data is hard to get, collection is time-intensive, and it's possible to spend months collecting data and see no improvement. Diagnose first — cheap knobs come before expensive ones.

QUICK CHECK

A model reaches 99% accuracy on the training set but only 84% on the validation set. Which single change targets this problem best?

Why: the 99%-vs-84% gap is a variance problem — the model is memorizing. Dropout is a regularizer, so it targets exactly this symptom. More epochs or a deeper network add fitting power, which widens the gap further; a different optimizer mainly changes how fast training error falls, not how well the model generalizes.

Tuning

Which hyperparameters to tune, and in what order

Many of the knobs above are settings of the training process — the hyperparameters. They can't all be tuned at once, and they don't matter equally.

Tune first

  • Learning rate α — most model failures trace back here

Tune next

  • Momentum β (0.9 is a good default)
  • Number of neurons / hidden units
  • Batch size

Tune last

  • Number of layers — changes the network entirely
  • Learning rate decay
  • Adam's β₁, β₂, ε — rarely worth it

Testing the claim: five learning rates, everything else held fixed

The same baseline is trained five times from the same starting weights with the same optimizer — the only thing that changes is the learning rate.

Final validation loss after 10 epochs, by learning rate (lower is better)

The two extremes do badly: 0.00001 barely moves the loss in 10 epochs, and 1.0 makes it jump around. Only the middle values — 0.001 and 0.01 — train properly. Same data, same network, same optimizer: one number decided whether the model learned at all.

Why search the learning rate on a log scale?

The useful range spans several orders of magnitude, roughly 10⁻⁵ to 10⁻¹. Sampling uniformly between 0.00001 and 0.1 puts about 90% of samples above 0.01 — small values are almost never tested. Sampling the exponent uniformly instead gives every order of magnitude equal attention.

Grid search doesn't scale — random search does

Grid search trains one model per combination of hyperparameter values. As the number of hyperparameters grows, the number of combinations — and the compute bill — grows very fast. The usual fix: run a cheap random search first to find the promising region, then grid-search inside it.

QUICK CHECK

You can afford 25 training runs to tune two hyperparameters: the learning rate, which matters a lot, and the batch size, which matters little. Why is random search usually better than a 5×5 grid here?

Why: in a 5×5 grid, every learning rate repeats 5 times with different batch sizes, so only 5 distinct learning rates are ever tried. Random search samples a new value for every hyperparameter on every run, so 25 runs test 25 distinct learning rates — a far better chance of landing near the best value when one hyperparameter dominates.

Verification

Gradient checking

So far, every fix assumed the training machinery itself works. But what if the loss refuses to go down even after the right knobs are turned? One possibility: a bug inside backpropagation. PyTorch's autograd computes gradients for built-in layers automatically, so this mostly matters for custom layers, custom losses, or a hand-written backward pass.

Approximating a derivative numerically

Take a function, say f(x) = x³, and two points around x = 2: p = x + ε and q = x − ε. The slope of the line through them approximates the true derivative:

f'(x) ≈ [ f(x+ε) − f(x−ε) ] / 2ε

—Numerical approximation
12.0000Exact derivative, f′(x)=3x²=12
—Absolute difference

Drag the slider. As ε shrinks the approximation converges toward the true derivative — this is the mechanism gradient checking relies on, applied to every value in a network's weights instead of one toy function.

Scaling it to a whole network

Every layer's weights and biases are unrolled into one flat vector θ, so the loss becomes a function of θ alone. The same finite-difference trick is then applied to every value in θ, one at a time, and compared against the gradient backpropagation actually computed — this is slow (two forward passes per value), so it's used for debugging only, never during training, and it needs 64-bit floats, since 32-bit rounding error can swamp a step of ε = 10⁻⁷.

The two gradient vectors are compared with a relative-difference score: ≤ 10⁻⁵ means no issue; above that, something in backpropagation is wrong, and a value around 10⁻³ or higher is almost certainly a bug.

View the relative-difference check 
def relative_difference(a, b):
    return (torch.norm(a - b) / (torch.norm(a) + torch.norm(b))).item()

def report(grad_numeric, grad_analytic, model):
    print("whole network", relative_difference(grad_numeric, grad_analytic))
    start = 0
    for name, p in model.named_parameters():
        end = start + p.numel()
        print(name, relative_difference(grad_numeric[start:end],
                                         grad_analytic[start:end]))
        start = end
Relative difference, per layer — correct code vs. a planted bug

Every layer sits far below the 10⁻⁵ threshold — backpropagation is correct for this network.

Notice what the buggy report does: it doesn't just say something is wrong, it says where. Only the last layer's bias spikes, so that's exactly where to look for the bug — not the whole network.

Does gradient checking work with dropout?

No. Dropout silences different neurons on every pass, so the loss changes randomly between the two forward passes and the numerical gradient becomes meaningless. Switch dropout off while checking.

QUICK CHECK

A gradient check on a network with custom layers gives a relative difference of 10⁻⁹ for every layer except one, whose weight gradient shows 0.8. What should you do next?

Why: 10⁻⁹ in every other layer means backprop matches the numerical gradient almost everywhere. The 0.8 value shows the analytic gradient for that one layer's weights is wrong — the bug lives in its backward code. Learning rate, data volume, and epsilon size don't change whether the analytic gradient is correct.

Measurement

A single evaluation metric

Backpropagation is verified and the right knobs are known. The next question: after every experiment, how do you decide a new model is actually better? Tracking precision and recall separately doesn't settle it — they don't always agree.

F1: combine precision and recall

Model A: precision 68%, recall 35%. Model B: precision 64%, recall 40%. Which is better? On raw numbers, it's an argument — A wins on precision, B wins on recall. The F1 score, the harmonic mean of the two, settles it by punishing a model that's excellent at one thing and poor at the other.

—Simple average
—F1 score

Try precision 0.95 / recall 0.30 (average 0.625, but F1 only 0.456), then precision 0.60 / recall 0.55 (average 0.575, F1 0.574) — F1 favors the balanced model even though its average is lower.

When metrics can't be combined: optimizing vs. satisficing

F1 score and running time can't be merged into one sensible number. The fix: pick one optimizing metric to maximize, and put a threshold — a satisficing constraint — on the rest. In practice the satisficing metrics are usually engineering limits like latency or memory, and the optimizing metric is quality.

ModelF1 scoreRunning time
A80%100ms
B92%180ms
C95%250ms

Maximize F1 such that latency ≤ 200ms → Model B (C is too slow). Raise the threshold to 300ms → Model C. The threshold itself comes from the business, not the data — a fraud check has to finish before the payment screen times out.

A surprise about micro-averaged F1

For a single-label problem, every wrong prediction is counted twice — once as a false positive for the predicted class, once as a false negative for the true class. Pooled across all classes, micro precision, micro recall, micro F1, and plain accuracy all collapse to the same number.

0.5153Macro F1

Accuracy, micro precision, micro recall and micro F1 are all identical — only macro F1 differs, and here it differs only slightly.

0.95Accuracy

0.487Macro F1

A model that never once finds the minority class still scores 0.95 accuracy and micro F1. Macro F1 — which treats every class equally — collapses to 0.487, because that class's F1 is 0. Macro averaging is what exposes a classifier that's secretly just predicting the majority class.

QUICK CHECK

A single-label classifier with four classes always predicts the majority class, which covers 90% of the data. Which metric exposes this problem?

Why: for single-label multi-class data, micro precision, recall and F1 all equal accuracy — each would report 90% and hide the problem. Macro F1 computes each class's F1 first, then plain-averages. The three never-predicted classes score 0, dragging macro F1 well below 90%.

Keep validation and test from the same distribution

On the held-out test set, the model scores a macro F1 of 0.5047 — close to validation's 0.5153, because both sets are drawn from the same distribution. If validation held only one region's customers and test held another, the two sets would describe different populations, and a validation score would say nothing about test performance. The fix: pool all the data, shuffle, then split — this is the day-to-day version of the production problem called distribution shift.

Judgment

Human-level performance & Bayes error

A macro F1 of roughly 0.5 — is that good? A number alone means nothing; it needs something to compare against.

Trivial baselines

  • Random guess among 4 classes: ~25%
  • Always predict the majority class: 25.6%
  • Our model: ~50% — clearly learned something

But is 50% good enough?

  • If a human scores 60% on the same task, the model is still behind
  • Most business problems want the model at or beyond human performance

There is always some irreducible error in any dataset — noise, ambiguous cases, overlapping classes, occasionally wrong labels. The lowest error any model or human could possibly reach is the Bayes optimal error. Since we rarely know it exactly, human-level performance is used as its proxy — which makes it a very useful reference for deciding whether to fight bias or variance.

Avoidable bias vs. variance — try it

Avoidable bias is the gap between human (Bayes-proxy) error and training error. Variance is the gap between training and validation error. Enter three numbers and see which one dominates:

Defaults: a car-classification task where human error is 1%, training error 7%, validation error 9% — bias dominates. Switch human error to 6.5% (say, the images turn blurry) and the same training/validation errors suddenly point to variance instead. Same model, same errors, two different next steps — the human reference is what tells you which.

With several human benchmarks — an average person at 3% error, a doctor at 1%, a team of experts at 0.5% — which counts as "human error," and which as the Bayes proxy?

The specialist in the field (the doctor, 1%) is the human-error reference; the best attainable group (the expert team, 0.5%) stands in for Bayes optimal error — the lowest error that can be attained is always the best available estimate.

QUICK CHECK

For a task, the best human expert team makes 2% error. A model has 3% training error and 8% validation error. What should you work on first?

Why: avoidable bias is 3% − 2% = 1%. Variance is 8% − 3% = 5% — five times larger. The model already fits close to human level; it just doesn't generalize. Regularization or more diverse data attacks that gap, while a bigger network or longer training would only chip away at the small bias term.

When tuning stops helping: error analysis

Once hyperparameter tuning only moves the needle slightly, the next step is manual: take the misclassified validation samples, count them by class, and work on whichever class accounts for the largest share of mistakes — fixing it removes the most error for the least effort.

Using an AI assistant safely for error analysis

A confusion-matrix summary is exactly the kind of thing an AI assistant can help reason about — but raw customer rows must never be pasted into an external tool. Share only aggregated numbers.

  1. Share the misclassification table and confusion matrix as aggregated text, never raw rows.
  2. Ask the assistant for a few hypotheses about why specific classes get confused.
  3. Pick one hypothesis and test it directly against the validation data.
  4. Report whether the data actually supports it.

Extension

Multi-task learning

Every customer so far carried exactly one label. What if a single input can carry several labels at once — an autonomous-vehicle frame that contains both a stop sign and a car?

The classical approach

  • Train 4 separate models — one per object
  • No information shared between them
  • 4× the inference compute, every frame

The neural network approach

  • One output layer, 4 neurons — one per object
  • Hidden layers share features across all 4 tasks
  • One forward pass answers all four questions — this is multi-task learning

Why sigmoid, not softmax, for the output

Softmax picks one class among several — its outputs compete and sum to 1. Here, several tags can be true in the same frame at once, so each one is its own independent yes/no question: sigmoid with binary cross-entropy.

Same four scores, two different output functions
Softmax (competes, sums to 1) Sigmoid (independent probabilities)

With softmax, the stop-sign score (0.62) pulls the car down to 0.14 — they're competing for the same probability mass. With sigmoid, car gets 0.82 and stop sign gets 0.95 at the same time — exactly what's needed when both are genuinely in the frame.

QUICK CHECK

A single network must tag every photo with any combination of "beach," "dog," and "sunset." Several tags can be true in the same photo. Which output layer and loss fit this problem?

Why: a photo can contain a beach, a dog, and a sunset at once, so each tag is its own yes/no question. Sigmoid treats every tag independently, and binary cross-entropy is the matching loss. Softmax forces the probabilities to sum to 1, making the tags compete as if only one could be present.

The trade-off, in interview terms

One multi-task network shares hidden features (which can improve every task) and needs only one forward pass (lower inference cost and latency). The risk: tasks can interfere when they need very different features, or when one loss dominates the others. This matters most when the compute or latency budget is genuinely tight.
